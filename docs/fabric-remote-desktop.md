# Fabric Remote Desktop (one-click, zero-CLI)

Goal: from Cerebro, click **Remote Desktop** on a Fabric agent and get a GUI session in the
browser (noVNC / guacd) plus the existing **Files** tab — with **no command line before or
after installing the agent**. Parallels today's Windows (RDP), macOS (VNC), and headless
Linux (SSH) remote-control + SFTP.

## Architecture — auto-pick ladder
The agent gains two control frames alongside the existing `open-stream`/`set-allow`/… :
`desktop-start` and `desktop-stop`. On `desktop-start` the agent picks the best available
mode, provisions it, and returns `{ proto: 'rdp'|'vnc', port, username, oneTimeSecret }`.
Cerebro then brokers that port exactly like any RDP/VNC route and opens it in the browser.

Mode selection, per host:
1. **Real logged-in session, via the OS's own remote desktop** (no bundling):
   - Linux + Wayland (Ubuntu 22.04+ default): drive **`gnome-remote-desktop`** (RDP) with
     `grdctl` — enable, set a generated one-time credential, read the TLS cert. This is the
     only way to see the *actual* Wayland screen. GNOME-specific; `grdctl` syntax differs
     22.04 vs 24.04 (handle both).
   - Linux + Xorg: attach the bundled VNC server to display `:0` (mirrors the real screen).
   - Windows: already RDP (unchanged). macOS: Screen Sharing/VNC (unchanged).
2. **Bundled virtual desktop** (fallback — headless servers / no usable real session):
   the agent launches a self-contained **Xvnc + minimal window manager** bundled in the
   agent binary, as the box's desktop user, on a free display. Works on Wayland and Xorg
   because it's its own X server. A *separate* session from the physical monitor.

"Real session where supported, else a bundled virtual desktop" is the reconciliation of the
two build choices (real-session can't be bundled on Wayland — it IS the OS's grd).

## Bundling (the heavy part — build-side)
The virtual-desktop server (Xvnc + a tiny WM like `openbox`, plus minimal xkb/fonts) is
embedded via `go:embed` under `agent/desktop/<goos>_<goarch>/` and extracted to a private
runtime dir on first use. The agent build must place those native binaries there per arch
(amd64/arm64) — they are NOT in the repo. Expect the agent binary to grow by tens of MB.
Licensing: TigerVNC (GPLv2) / openbox (GPLv2) ship as separate executables we invoke, not
linked — fine to distribute alongside.

## Security & lifecycle
- The GUI server binds to **loopback on the agent**; only the agent brokers it over the
  tunnel (same model as every other route). Never a listening port on the LAN.
- A **one-time, per-session credential** is generated by the agent and handed to Cerebro for
  that session only; rotated/cleared on stop.
- Runs as the **box's desktop user** (resolved via `loginctl`), never as the root agent.
- **Idle teardown**: the agent stops the server (and, for grd, reverts the enable) on
  disconnect or an idle timeout; `desktop-stop` forces it. Audited via the Fabric audit feed.

## File transfer
Unchanged and already works: add an **`ssh` route** to the box → the existing SFTP file
browser ([fabric-sftp.service.ts](../apps/server/src/fabric/fabric-sftp.service.ts)). Desktop
boxes use the same path as headless Linux. (SFTP is SSH-only by design.)

## Phases
- **P1 — Real session on actual desktops (no bundling).** Control frames + session model +
  `desktop_linux.go` doing the Wayland/`gnome-remote-desktop` path (and Xorg attach), server
  orchestration (`desktop-start/stop` → auto RDP/VNC route), one-click **Remote Desktop**
  button + status in the Fabric UI. Delivers the Ubuntu-Desktop ask, zero-CLI, nothing to
  bundle. (Windows/macOS already have their native path.)
- **P2 — Bundled virtual desktop for headless.** Embed Xvnc + WM per arch, agent extract +
  launch-as-user + lifecycle; auto-fallback when no real session exists. The build-side
  bundling lands here.
- **P3 — Polish.** Idle-timeout tuning, multi-session, resolution/scaling, macOS/Windows
  one-click parity, a "set up a desktop on this headless box" affordance.

## Build note
No Go toolchain in the authoring environment, so the agent code is written but compiled by
the normal agent build. Server + web changes are built/verified here as usual.
